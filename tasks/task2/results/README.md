## Что сделано

- `booking-service` на Python: gRPC по `booking.proto`, своя база `booking-db`. Проверки берёт у монолита по REST, расчёт
цены перенёс из монолита как есть. После брони отправляет `BookingCreated` в Kafka.
- `booking-history-service` читает события и пишет их в свою базу. Статистику по пользователям, отелям и дням считают
представления `stats_by_user`, `stats_by_hotel`, `stats_by_day`.
- В монолите поправил `BookingController`: создание идёт в `grpcBookingService`, список остался на старом
`bookingService`. Jar пересобран.
- Образа `openjdk:17-jdk-slim` больше нет, монолит теперь на `eclipse-temurin:17-jre`. Тестер не собирался на bullseye,
перевёл на bookworm.

## Миграция данных при запуске

Старые брони не переносим. Новые пишутся только в `booking-db`, старые остаются в базе монолита, список читает её.
Откат - убрать `BOOKING_SERVICE_EXTERNAL_HOST` у монолита.

Минус: бронь, созданную через новый сервис, не видно в старом списке монолита, только через сам сервис. Поэтому
переключение списка надолго не откладываем. Id в новой базе свои и могут пересечься со старыми, при переносе это надо
учесть.
