# Задание 2. booking-service и booking-history-service

## Что сделано

- `booking-service` на Python: gRPC по `booking.proto`, порт 9090, своя база `booking-db`. Проверки пользователя,
отеля, отзывов и промокода берёт у монолита по REST, расчёт цены перенесён из `BookingService.java` как есть. После
сохранения брони отправляет `BookingCreated` в Kafka, топик `booking.created`.
- `booking-history-service` на Python: читает `booking.created` и пишет события в `booking_history` своей базы
`booking-history-db`. Статистику для аналитиков (по пользователям, отелям, дням) считают представления
`stats_by_user`, `stats_by_hotel`, `stats_by_day`. Боевую базу монолита сервис не трогает.
- Монолит: в `BookingController` создание брони идёт в прокси `grpcBookingService`, а список - в старый
`bookingService`. Без этой правки прокси забирал и список, а по заданию он должен работать как раньше. Jar пересобран
и лежит в `tasks/monolith/`.
- Окружение: образа `openjdk:17-jdk-slim` больше нет на Docker Hub, в `tasks/monolith/Dockerfile` теперь
`eclipse-temurin:17-jre`. Тестер не собирался на `debian:bullseye-slim`, перевёл на `debian:bookworm-slim`.

Запуск: `docker compose down` в `tasks/task1`, затем `docker compose up -d --build` в `tasks/task2`.

## Стратегия миграции данных при запуске

Старые брони никуда не переносим. Создание брони переключается на новый сервис, и новые брони пишутся только в
`booking-db`. Старые остаются в базе монолита, а список броней по заданию продолжает читать её. Получается, что в
момент запуска ни одна строка не копируется и откатиться можно, просто убрав `BOOKING_SERVICE_EXTERNAL_HOST` у
монолита.

Цена этого решения: бронь, созданная через новый сервис, не видна в старом списке монолита. Её видно через
`ListBookings` сервиса и в личном кабинете. Поэтому переключение списка нельзя надолго откладывать.

Идентификаторы: в новой базе своя последовательность id. Пересечение с id монолита возможно, при переносе старых броней
это придётся учесть (сдвинуть последовательность или хранить старый id отдельно).

## Стратегия To-Be

1. Разовая выгрузка старых броней из таблицы `booking` монолита в `booking-db`.
2. До переключения изменения в старой таблице доносятся в новую базу через CDC (Debezium читает журнал Postgres
монолита и пишет в Kafka). Писать сразу в обе базы не стал: при сбое одной из записей они разъедутся.
3. Сверка количества и сумм по броням в двух базах.
4. Список броней в монолите переключается на `grpcBookingService` (одна строка в контроллере), затем клиенты уходят на
сервис напрямую или через GraphQL.
5. Таблица `booking` и старый `BookingService` удаляются из монолита.

Дальше выносятся промокоды, отели и отзывы, пользователи. В booking-service меняется только `app/monolith.py`, который
сейчас знает про REST монолита.

## Тесты

В `regress.sh` добавлены проверки нового сервиса, они включаются переменными окружения, без них тест работает как
раньше по одному монолиту. Перед тестами очищаются таблицы новых баз, тест ждёт booking-service, после броней
проверяет, что они попали в `booking-db` с теми же ценами, что дал бы монолит, что список в монолите не изменился и
что события дошли до истории. Фикстуры не менял.

По логам видно, что два отказа срабатывают не по той причине, что в названии теста: `test-hotel-3` отклоняется,
потому что не работает, а `test-hotel-2` - потому что ему не доверяют (один отзыв). Ветка «нет мест» реально не
проверяется. Так было и до переноса.
