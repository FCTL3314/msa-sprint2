### <a name="_b7urdng99y53"></a>**Название задачи: Целевая архитектура Hotelio и состояние через два месяца**
### <a name="_hjk0fkfyohdk"></a>**Автор: Никита Соловьёв**
### <a name="_uanumrh8zrui"></a>**Дата: 12.10.2026**

### **Проблема**
Бронирование отелей, около 1 млн пользователей, основной трафик - поиск и бронирование. Всё живёт в одном Spring Boot
приложении с одной базой. Бэкенд пишут три человека: два Java-разработчика и архитектор.

Проблемы из постановки:
1. Сложно сопровождать: любое изменение требует понимания всей кодовой базы.
2. Бронирование нельзя масштабировать отдельно, хотя пик нагрузки приходится именно на него.
3. Команды не могут работать и выпускаться независимо, быстрый CI/CD не внедрить.
4. REST монолита неудобен фронтенду, BFF нет.
5. Новые фичи рискованные: всё связано, тестировать приходится всё.

Что нашёл сам, в коде и на запущенном монолите (проверки в `test-log.txt`):

6. `BookingService` синхронно вызывает четыре других модуля, и все они работают с одной базой. Отсюда растут проблемы
1, 2 и 5: ни один модуль не вынести, не задев бронирование.
7. `ddl-auto: create` - схема базы пересоздаётся при каждом старте. Перезапуск монолита стирает все данные.
8. Ошибки в расчёте брони. Цена не зависит от отеля, база 100 или 80 для VIP зашита в коде. Скидка промокода
вычитается суммой, и эта сумма пишется в поле `discountPercent`: VIP с промокодом на 10 платит 70. Срок действия
промокода `validUntil` не проверяется. Дата брони `createdAt` у новых броней пустая.
9. Нет аутентификации. `userId` приходит параметром запроса, а `GET /api/bookings` без него отдаёт брони всех
пользователей.
10. Отказ в бронировании (пользователь неактивен, мест нет) приходит как 500, клиент не отличит его от падения сервера.
11. Описание API расходится с кодом: у отеля в документации есть `name` и `pricePerNight`, в модели их нет.

### <a name="_qmphm5d6rvi3"></a>**Решение**
Цель через год. Монолита нет, по сервису на модуль: бронирования, пользователи, отели, отзывы, промокоды, и отдельно
история со статистикой. У каждого сервиса своя база. Синхронные проверки идут по gRPC, события между сервисами через
Kafka. Фронтенд ходит через API Gateway в GraphQL-шлюз, партнёры через тот же API Gateway в REST. Всё развёрнуто в
Kubernetes с Istio: постепенная выкладка версий, метрики и трассировка без правки кода сервисов. Выполняем НФТ 1, 2,
5, 6 и 7.

[c2-target.puml](diagrams/c2-target.puml)

![C2, через год](diagrams/c2-target.png)

Ближайшая цель - состояние через два месяца, его и проектирую подробно. Вынесены бронирование, история со статистикой и
промокоды на уровне GraphQL. В монолите остаются пользователи, отели, отзывы, данные промокодов и старый список броней.
Монолит больше не дорабатывается, новые фичи пишем только в новых сервисах.

[c2-intermediate.puml](diagrams/c2-intermediate.puml)

![C2, через два месяца](diagrams/c2-intermediate.png)

- Создание брони монолит передаёт сервису бронирований по gRPC. Клиенты по-прежнему ходят в монолит, внешний API не
меняется. Выполняем НФТ 4.
- У сервиса бронирований своя база, первая отделённая от монолита. Сам сервис в Kubernetes, его можно масштабировать
числом реплик. Выполняем НФТ 1.
- После сохранения брони сервис отправляет событие в Kafka. Сервис истории собирает из событий статистику в свою
базу, аналитики смотрят её там. Выполняем НФТ 6.
- Личный кабинет идёт через GraphQL-шлюз с подграфами бронирований, отелей и промокодов. Проверка, что брони свои,
уже на уровне GraphQL. Выполняем НФТ 3.

Почему первым именно бронирование и по каким шагам переносим - в ADR-002.

Как закрываются проблемы:

|**Проблема**|**Решение**|
| :-: | :- |
|1, 6|Модули становятся сервисами со своими базами, общаются только через API и события. По одному модулю за раз, НФТ 8|
|2|Сервис бронирований отдельно в Kubernetes|
|3|У каждого сервиса свой Helm-чарт и пайплайн CI/CD|
|4|GraphQL Federation как BFF, каждый домен своим подграфом|
|5|Регрессионные тесты на каждом шаге, канареечная выкладка и фича-флаги через Istio|
|7|Миграции схемы в новых сервисах. В монолите заменить `create` на `validate`: правка в одну строку, и я бы сделал её исключением из правила «монолит не дорабатываем», речь о потере данных|
|8|В сервисе бронирований поведение сохраняем как есть, чтобы перенос ничего не поменял для клиентов. Исправлять расчёт - отдельная задача вместе с продуктом. Срок промокода проверяет новый подграф промокодов|
|9|Через год - API Gateway с проверкой токена, `userId` берётся из токена. До этого - проверка в GraphQL|
|10|Новый сервис отдаёт отказ отдельным кодом gRPC. Перевести ответ монолита на 4xx можно, когда клиенты будут готовы|
|11|Контракт задаётся явно: `booking.proto`, схема GraphQL|

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Переписать систему целиком и переключиться за один раз. Три бэкенд-разработчика на несколько месяцев без новых фич,
а весь риск переключения ложится на один день. Не подходит.

Модульный монолит: навести границы между модулями в коде, но оставить одно приложение и одну базу. Дешевле, частично
закрывает проблемы 1 и 5. Но бронирование по-прежнему не масштабируется отдельно и выкладывается вместе со всем,
проблемы 2 и 3 остаются. Для модулей, до которых очередь дойдёт не скоро, я бы делал это параллельно с выносом.

Только API Gateway, без GraphQL. Он маршрутизирует и проверяет доступ, но не собирает в один ответ данные из нескольких
сервисов. Личному кабинету нужен именно сбор, поэтому в целевом состоянии есть оба.

**Недостатки, ограничения, риски**

- Данные разъезжаются по базам. Согласованность между сервисами держится на событиях, а не на транзакции,
статистика отстаёт от реальных броней.
- Вызов в памяти становится сетевым. У брони пять проверок, задержка вырастет.
- Kubernetes, Istio, Kafka и несколько баз ложатся на одного DevOps-инженера. Это я бы считал главным риском плана.
- Пока монолит жив, сервис бронирований зависит от его доступности.
- Ошибки расчёта брони (проблема 8) переезжают в новый сервис вместе с логикой.
